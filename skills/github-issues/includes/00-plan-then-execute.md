# 先规划，再执行（总流程）

本技能对**会改动 GitHub、上传资源或修改仓库代码**的操作，默认采用 **两阶段**；各子流程的具体细则见对应 include，**本文件为总纲**。

---

## 两阶段模型

| 阶段 | 名称 | 做什么 | **禁止** |
|------|------|--------|----------|
| **A** | **规划** | 理解意图；只读检索（`gh issue view`、`rg`、Read、下载附件到本地只读）；在对话中输出**计划 / 方案 / 草案**；**明确停止并等待用户确认** | 改业务代码、`git commit`、`git checkout -b`、跑迁移、`gh issue create/comment/edit`、`gh gist` 写操作、上传 docx/图片、批量发帖脚本 |
| **B** | **执行** | 用户确认（如「可以」「按这个做」「发吧」）后，打开对应 include 动手，并完成 push / PR / 评论等收尾 | 在用户未确认前进入本阶段 |

> **只读帮助**（如 `gh issue list`、解释某条 issue 且不改 GitHub、列出 Gist）→ **仅阶段 A 中的检索**，无需等待确认即可回复。

---

## 各场景：规划产出 ↔ 执行入口

| 用户意图 / 触发语 | 阶段 A 须输出的内容 | 用户确认后打开 |
|-------------------|---------------------|----------------|
| **解决 #xxx**、修/处理/搞定 #N、issue URL | **修复规划**：问题摘要、根因假设、改动范围与主要路径、步骤、风险、验证（见 [`03-issue-fix.md`](03-issue-fix.md) 阶段零 / 两步走第 1 步） | `03` 阶段四起：从 `dev` 建修复分支 → 编码 → push → **`gh pr create`（base `dev`）** → issue 评论附 PR 链接 |
| **解读** #xxx、分析 issue、批量解读 | **拟发布的 `## 🔍 Issue 解读` 全文**（含可执行修复方案、相似 OPEN issue 结论） | `02` Step R5 发帖 + Step R6 追加标签 |
| **Word / docx 建 issues** | 文档路径、防重复结论、预计条数、标签策略、**标题草案列表** | `01` Step 1～10 |
| **口述建 issue** | 标题、标签、body 要点草案 | `04` Step V1～V6 |
| **Gist 创建/编辑**（参数已齐） | 标题与内容摘要（用户要求预览时） | `09` |
| **先解读再解决** | 先完成解读规划并发帖确认；解决须**再次**走 `03` 修复规划（除非用户一次性批准整体方案） | 依次 `02` → `03` |
| **批量扫描 / 脚本发帖** | 影响范围、条数、**至少 1 条样例全文**、是否跳过已解读 | `02` 批量节或 `scripts/` |

## 确认话术与停损

**阶段 A 结束时**，须用一句话请用户确认，例如：

> 以上是 [解决 #123 / 解读 / 建 issue …] 的规划（或草案）。请回复「可以开始」「通过」或提出修改；确认后我再执行。

- 用户要求改规划 → 修订后**再次**等待确认。
- issue 描述不清、截图无法判断、业务规则不确定 → **先向用户提问**，再输出规划；**禁止猜测后直接编码或发帖**。

---

## 豁免（可跳过阶段 A，直接进入执行）

仅当用户**同一条消息或本会话中已明确**表达，例如：

- 「直接执行」「跳过规划」「不用确认」「直接改」「先写代码」
- 「直接建」「直接发」「发吧」（针对建 issue / 解读发帖）
- 「按解读里的方案做」（且 issue 下已有含「可执行修复方案」的 **`## 🔍 Issue 解读`**）
- 同一会话中用户**已对同一任务**表示通过（「可以」「OK」「按这个来」）

---

## 与「解读」和「解决」的分工

- **解读**（`02`）：把可执行方案写到 issue 评论；默认**发帖前**在对话展示全文并确认。
- **解决**（`03`）：即使用户刚确认过解读帖，**默认仍须**再走修复规划（阶段零）；除非用户明确「按解读直接改」或上文豁免。

## 流程示意

```text
用户请求
    │
    ▼
是否只读？ ──是──► 检索后直接回复
    │
    否
    ▼
用户是否已豁免规划？ ──是──► 阶段 B（对应 include）
    │
    否
    ▼
阶段 A：只读分析 + 对话输出计划/草案
    │
    ▼
等待用户确认 ──否/要改──► 修订计划 ──┐
    │                              │
   确认 ◄──────────────────────────┘
    │
    ▼
阶段 B：执行（gh / 改代码 / push / PR / 评论）
```
