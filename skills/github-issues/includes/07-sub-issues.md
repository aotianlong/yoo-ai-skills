# 子 Issue 与父 Epic 的处理

当仓库用 **父 issue + 多条子 issue**（或在评论中用「子任务拆分」枚举 `#26` `#27` …）组织工作时，AI 必须在**只读分析阶段**理清关系，避免误关父 issue、或漏做仍在 OPEN 的子任务。

## 何时适用

- Issue **正文**出现：`父任务`、`Parent`、`Blocked by`、`子任务`、`## 子任务`、指向其它 `#数字` 的清单。
- Issue **评论**（含脚本自动评论）中列出：`以下子 Issue`、`- #26`、`- #27` 等。
- GitHub **子 issue / Track sub-issues**（若仓库已启用）在界面中展示的层级；或用 **`gh issue view N --json parent`**（`gh` 新版本字段依 GitHub API 而定，无则仍以正文+评论为准）。

## 发现子 issue 的推荐步骤（只读）

1. `gh issue view <N> --repo OWNER/REPO --comments`（或 `--json comments`）通读**全部评论**。
2. 在 body 与评论中搜索：`#[0-9]+`、`子`、`sub`、`parent`、`父`、`epic`。
3. 对每个疑似子编号执行 `gh issue view <子编号> --json title,state,body`，确认其 **body 是否反查父任务**（例如「父任务：#16」）。
4. 汇总表格（建议写入「修复规划」）：`#子编号` | `state` | `title` | `与本次「解决父/子」是否相关`。

## 父 issue vs 子 issue：范围与「解决」含义

| 情形 | 建议 |
|------|------|
| 用户说 **「解决 #父」** 且父为 **Epic/模块总览**，子任务 **全部仍为 OPEN** | **第 1 步规划中必须写明**：父 issue 的验收是否允许「只交付总览文档/索引」即可勾选；若不允许，应列出**须先完成的子 issue 列表**或建议用户改口为「解决 #子」。**禁止**在未对齐验收的情况下默认 `Closes #父`。 |
| 用户说 **「解决 #子」** | 按普通单 issue 走 [`03-issue-fix.md`](03-issue-fix.md)「两步走」；PR 中 `Closes #子`；若修复顺带满足父 issue 某条验收，可在父 issue **评论说明关联**，是否关父 issue 由验收与子任务完成情况决定。 |
| 用户要求 **一次性解决父+全部子** | 阶段三「分组」时按模块/文件合并分支；或按子 issue **分组多 PR**（每 PR 仍 `push` + `gh pr create`），**每个**被修复的 issue 做 Step D 总结评论。 |

## 关闭策略（默认保守）

- **默认**：**不因**「只改了父 issue 文档」就 **`Closes #父`**，除非父 issue 正文验收明确要求仅为文档/对齐，且**无**未完成的强制子验收与之矛盾。
- 子 issue **全部关闭**且父 issue 验收条目已满足 → 父 issue 可关，评论中汇总子 issue 链接与结论。
- 若父 issue 与 **#子列表** 重复定义验收：以**范围更细、更新更近**的为准；冲突时在父 issue **提问或评论**澄清后再关。

## PR 与 GitHub 关键词

- 单 PR 只对应部分子 issue：body 使用 `Closes #26`、`Closes #27` 等**实际由本 PR 解决的编号**；不要写未包含在本次 diff 中的 `Closes #父`。
- 父 Epic 若仅进度更新：用 `Refs #16` / 评论关联，避免错误关闭。

## 与「两步走 / 阶段零」的衔接

- **Step Z1 / Z2**：若存在子 issue，规划里必须包含 **子 issue 清单与 state**、本次工作覆盖**父/哪些子**、以及**关闭策略**（是否关父、是否只关子）。
- **Step Z3**：若用户对「只关父/先关子/全部做完再关」未表态，**必须先问清再等待确认**。

## 与解读流程的衔接

- 解读 **父 Epic** 时，在「相似/关联 OPEN issue」中列出 **OPEN 的子 issue**；若子 issue 已含更细复现路径，父 issue 解读可简要引用「详见 #子」。
